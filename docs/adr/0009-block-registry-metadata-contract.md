# ADR 0009 — Traceable block decomposition: a pattern, on Tree, with a metadata sidecar

**Status:** accepted (v2.6.13)

## Context

Some documentation needs a component cited by a stable identifier, not just shown in a picture — compliance records, IP/patent-support documentation, and any audit trail where a reader must point at one specific structural element and know it will keep resolving to the same thing later, not just to "the box near the middle." Nothing in this skill's existing type/pattern set gives a block that kind of addressable identity: every diagram shows structure, but nothing lets a reader cite one specific block directly, trace it to its parent, to what it consumes and produces, and to the code that implements it.

The brief that first proposed this cited a governing military standard by number. Neither number checked out against a primary source: the first is a real standard, for solderless wire-wrap electrical connectors, unrelated to diagrams; the second does not exist in any standard index. That both were confidently wrong is the reason this ADR insists on primary sources for what it does cite: IDEF0 (FIPS PUB 183) is the real standard for hierarchical *functional* decomposition, read directly from the primary source rather than a secondhand description of it. It was not adopted — see Rejected below — but ruling it out is what led to the vocabulary decision in this ADR.

## Decision

Add one new semantic pattern, **Traceable block decomposition** (`references/semantic-patterns.md` § 8), routed to the existing **Tree** visual type. Not a new type, not IDEF0's four-sided ICOM grammar, and not a claim of formal SysML compliance — SysML-*informed* vocabulary (block, noun-phrase naming, flow port) applied honestly to Tree's existing layout grammar. `references/type-tree.md` points to the pattern from its own "Best for" line.

**Tree, not Nested or Architecture.** Architecture's zones are flat and hard-capped at 3 — no real nesting. Nested is a single concentric chain, one ring inside the next, with no way to show two children of one parent at all. Tree already has multi-child breadth, a single-parent-per-node constraint, and no back-edges, which is the exact "no orphan blocks, no cycles" shape this pattern needs — not a workaround built to fit, the shape the type already had.

**A pattern, not a type.** ADR 0002 fixed the taxonomy at a count that only moves for a genuinely new *layout* grammar; a new type would also require the full §10 shipping set (type reference, three example variants, gallery tab, budget row), and `SKILL.md` had 16 bytes of headroom under its 40,000-byte cap (ADR 0004) at the time this landed — nowhere near enough. A pattern costs one `semantic-patterns.md` section and a routing-table row in both `SKILL.md` and `semantic-patterns.md` itself; `verify-docs-sync.py` never reads `semantic-patterns.md`, so the type-count gate does not move. `scripts/verify-semantic-motion.py`'s `PATTERN_NAMES` list is what does move, and is this decision's own enforcement (see the ADR 0002 amendment recording the count).

**Noun-phrase block names, not verb-phrase.** The original brief demanded verb-phrase names ("Ingest Raw Video") — IDEF0's convention, because IDEF0 decomposes *functions*. This pattern decomposes a system's *structure* (a payment gateway, an auth service), which is what SysML's noun-phrase Block Definition Diagram convention is for. This is a correctness fix, not a style preference: the wrong convention would misdescribe what is actually being documented, independent of which standard is more current.

**A stable ID per block, shown as a badge — everything else in `data-block-*` metadata, not on the canvas.** This repo's own editorial-minimalism target (density 4/10, delete anything removable) is in real tension with wanting rich per-block metadata. The resolution is a three-tier visibility split: an ID badge, a name, and at most one short in/out port label live on the diagram, using existing primitives (the node-box type-tag chip, the Geist Mono sublabel slot) with zero new SVG grammar; the full record (inputs, outputs, constraints, assumptions, an implementation path) lives in `data-block-*` attributes on the node — precedented already by `type-polar.md`/`type-line.md`'s `data-*` chart attributes, each with its own dedicated validator; anything longer than a short phrase lives in the sidecar registry, regenerated on demand via `/diagram-design:export-diagram --registry` (`references/export-registry.md`), never hand-maintained.

**A dedicated structural checker, `scripts/verify-block-registry.py`**, modeled on `scripts/verify-geometry.py` (ADR 0005): stdlib-only, a dataclass per block, adversarial tests in both polarities (`scripts/test-verify-block-registry.py`). It checks ID uniqueness, parent resolution (every `data-block-parent` must match a `data-block-id` in the same file), presence of `data-block-name`, and cycles in the parent chain. It deliberately does not correlate a block's metadata against its drawn position or connector geometry — that is a different kind of check than the ones this pattern's metadata contract needs, and is left for a future version if it turns out to be needed, not silently assumed.

**Static only.** Per ADR 0001, this pattern has no animated form. Bespoke interaction (click-to-expand an ID, filter by block) is out of this skill's scope entirely, the same boundary ADR 0001 draws for every other diagram.

**Explicit non-claims**, stated in `semantic-patterns.md` § 8 itself: no OCL constraints, no XMI interchange, no tool-certified SysML conformance, and no IDEF0 compliance claim either. The pattern borrows SysML's naming vocabulary because it fits what is being documented — structure, not function — not because the output claims to be a SysML artifact.

## Rejected, with reason

- **IDEF0 / FIPS PUB 183** — the real, verifiable standard for hierarchical decomposition, and the one actually checked against its primary source. Rejected because it decomposes *functions* (verb-phrase, four-sided ICOM boxes with Input/Control/Output/Mechanism arrows on every side), and this pattern documents *structure*. Its rigor is real; its grammar is the wrong fit, and it does not fit Tree's connector rules regardless.
- **A second, new visual type** for this grammar — rejected on the ADR 0002 bar: nothing here is a new *layout*, only a new set of things a Tree node can carry. Same reasoning ADR 0002 itself gives for rejecting "UML activity diagram" as a type rather than routing it to existing grammars.
- **A hand-maintained metadata file alongside the diagram** (e.g. a separate YAML/JSON authored independently of the HTML) — rejected because it would create a second source of truth that can silently drift from the diagram it describes. The sidecar registry is generated *from* the diagram's own `data-block-*` attributes, never authored in parallel to them.
- **Drawing input/output arrows between blocks on the canvas** — that is a dependency graph's job (which explicitly permits multi-parent nodes and cycles this pattern forbids), not a tree's. Cross-block flow, if it must be drawn, routes to that type instead.

## Consequences

- The semantic-pattern count moves to eight; the visual-type count does not move at all. `verify-semantic-motion.py`'s `PATTERN_NAMES` list and the ADR 0002 amendment are the record of the first change.
- `commands/export-diagram.md` and `prompts/export-diagram.md` gain one flag, `--registry`, routed to a new reference (`export-registry.md`) that shares no logic with the SVG/PNG procedure in `export.md` — it is a metadata projection, not a rasterization.
- A diagram using this pattern now carries two independent, composable gates: `verify-geometry.py` (does a label mask collide with a node painted after it — unaffected by this pattern, since every new visible element lives fully inside its own block's node rect, which the checker already exempts) and `verify-block-registry.py` (does the metadata cohere as a tree). Neither reads the other's attributes.
- `data-block-*` is new vocabulary, but it follows existing precedent rather than inventing a new kind of extension point: `type-polar.md` and several of `type-line.md`'s and `type-scatter.md`'s chart variants already bind their own semantics to a dedicated `data-*` attribute family (for example `data-series`, `data-bins`, `data-ranks`, `data-name`), each with its own validator that does not read another contract's attributes. This pattern joins that same family, scoped the same way.
- This ADR is itself an instance of what the pattern is for: a dated, version-controlled record of why the documentation is shaped the way it is, made contemporaneously rather than reconstructed later — the same discipline a contributor using this pattern for their own compliance or IP-support documentation would want from it.
